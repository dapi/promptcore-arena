# Версии игры

Версия приложения хранится только в `package.json → version` и следует
[SemVer 2.0.0](https://semver.org/lang/ru/). Первый выпуск — **0.1.0**.
Git-тег выпуска — `v<version>`, например `v0.1.0`. Опубликованные теги и записи
выпусков не переписываются; исправление получает новую версию.

## Когда менять номер

| Изменение | Следующая версия |
|---|---|
| Совместимое исправление ошибки, текста или отображения | PATCH: `0.1.0 → 0.1.1` |
| Новая функция или существенное изменение механики | MINOR: `0.1.1 → 0.2.0` |
| Несовместимое изменение до стабилизации API | MINOR, с описанием миграции в CHANGELOG |
| Стабилизация публичного контракта | `1.0.0` |
| Несовместимое изменение после `1.0.0` | MAJOR: `1.2.3 → 2.0.0` |

Контракт приложения включает документированный запуск через npm, локальный
HTTP API и чтение сохранённых JSON-повторов. При оценке совместимости учитываем
поля запросов и ответов, доступность прежних повторов, контракт допустимых
действий модели и правила из `docs/rules.md`. Добавление необязательного поля
совместимо; удаление поля, изменение его смысла или отказ читать прежнюю запись —
несовместимое изменение. До `1.0.0` контракт ещё может меняться.

## Версия приложения и версия правил

- `appVersion` — версия приложения, например `0.1.0`. Сервер читает её из
  `package.json` при запуске через `src/version.mjs`. Она видна рядом с логотипом,
  возвращается в `/api/config`, записывается в новые матчи и отчёты плейтестов.
- `version` в состоянии движка и повторе — идентификатор правил, сейчас `arena/2`.
  Он определяет, какой движок воспроизводит бой. Исправление интерфейса или
  добавление редактора не требует менять правила.
- Если изменение механики требует другого расчёта старых записей, сохраняем
  старый движок и добавляем новый идентификатор правил одновременно с выпуском
  новой версии приложения.
- У старых матчей `appVersion` отсутствует; в сводке API он равен `null`.
  Не подставляем текущую версию вместо неизвестной исторической.

## Выпуск

1. Запиши изменения в `CHANGELOG.md`, собери их под заголовком будущей версии
   вида `## [0.1.1] — 2026-10-05`. Дата — фактический день выпуска.
   Оставь пустую секцию `[Unreleased]` для следующего цикла.
2. Закоммить код, документацию и журнал изменений. Рабочие изменения должны
   быть сохранены до запуска `npm version`.
3. Выполни одну подходящую команду:

   ```sh
   npm version patch -m "Release v%s"
   npm version minor -m "Release v%s"
   npm version major -m "Release v%s"
   ```

   Для предварительного выпуска допустима точная версия, например
   `npm version 0.2.0-rc.1 -m "Release v%s"`.

   Стандартные [хуки npm version](https://docs.npmjs.com/cli/v11/commands/npm-version/)
   запускают проверки и тесты до изменения номера, затем проверяют запись новой
   версии в CHANGELOG. npm создаёт коммит и аннотированный тег. Если проверка
   новой записи не прошла, поправь журнал; не используй `--force` и не публикуй
   незавершённый выпуск.
4. Отправь ветку и конкретный тег вместе, например:

   ```sh
   git push --atomic origin main v0.1.1
   ```

5. Перезапусти локальное приложение и обнови вкладку браузера. Проверь номер
   рядом с логотипом и в `/api/config`.

`npm run check:version` проверяет формат SemVer и наличие записи текущей версии.
GitHub Actions запускает проверки на main, pull request и тегах `v*`; у тега
номер должен точно совпадать с `package.json`. Сценарии не публикуют npm-пакет
и не выполняют деплой: игра запускается локально.
